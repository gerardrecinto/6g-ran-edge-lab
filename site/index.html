Everything here is synthetic. The scenario is six simulated devices across four slices, with demand rising on ticks 5 to 8 and mobility events on ticks 7 and 8. It is standards-inspired, not a 3GPP stack.






  
How it works

  
Small enough to read in one sitting, real enough to reason about an incident.

  

    
1
Schedule by slice
User equipment demand and channel quality feed a slice-aware scheduler. Control traffic outranks video, IoT and Wi-Fi offload.

    
2
Collect the KPIs
Each tick produces throughput, p95 latency, resource block use and edge CPU pressure. A rolling detector flags regressions and instability.

    
3
Emit it your way
A table, JSON lines, Prometheus metrics, and OpenTelemetry-shaped logs and traces, with ops files for systemd, Kubernetes and Prometheus rules.

  






  
Run it

  
A C++17 compiler and make. Docker works too.

  

    


make
make test
./build/ranedge-sim --ticks 10
./build/ranedge-sim --ticks 8 --json
./build/ranedge-sim --ticks 8 --metrics

    

    


./build/ranedge-sim --ticks 8 --edge-cpu-budget 0.5 --json

docker build -t ranedge-sim .
docker run --rm ranedge-sim --ticks 6 --json

      
The README links a bare-metal runbook, an observability guide and the ops files.

    

  






  
What this does not do
    
    
  • It is a lab model. It is not a 3GPP stack and was not measured against a real radio.
    • 
    
  • The numbers come from one fixed scenario. Changing the budget is the only knob this page exposes.
    • 
    
  • Anomaly thresholds are the repo's defaults. They are examples, not tuned alert policy.
